Uso autorizado y aislado. El laboratorio crea un binario SUID, una política de sudo demasiado amplia y un cron de root. Cualquiera con acceso local puede convertirse en root: úsalo solo en una VM desechable o un host dedicado, nunca en producción.

Ubuntu Server 24.04 · Laboratorio educativo

VulnServer

Un servidor deliberadamente vulnerable para practicar hardening y escalada de privilegios: tres caminos reales hacia root, auditoría, hardening con rollback y reinicio de estado entre sesiones.

  • 80/80 tests funcionales
  • 3 escenarios de escalada
  • Solo Bash sin dependencias de runtime
  • Juice Shop como aplicación web

Cómo funciona el ejercicio

Dos roles, un servidor. Uno lo endurece; el otro intenta comprometerlo. Ambos documentan.

  1. El propietario despliega el laboratorio con install.sh y da acceso a su pareja.
  2. El atacante enumera el host y la aplicación web.
  3. Obtiene un punto de apoyo como labuser y lee la flag USER.
  4. Escala a labpriv y lee la flag PRIVILEGE.
  5. Llega a root por cualquiera de los escenarios y lee la flag ROOT.
  6. El propietario aplica harden.sh con copias de seguridad.
  7. Se repite el ataque y se demuestra que los caminos están cerrados.

Los tres escenarios

Cada uno es independiente, se activa por separado y tiene su propio parche verificable.

A · Riesgo alto

Permisos de archivo

Un bit SUID sobre una utilidad estándar y un directorio escribible por todos. Demuestra por qué cualquier ruta escribible que se ejecute en un contexto privilegiado termina en root.

/usr/bin/find · /opt/vulnserver/lab/perms

B · Riesgo alto

Configuración de sudo

Una delegación mal acotada hacia la cuenta intermedia permite saltar de labuser a labpriv sin explotar ningún binario del sistema.

sudoers drop-in · cuenta labpriv

C · Riesgo alto

Tarea cron de root

Un script escribible por un usuario se ejecuta como root cada minuto. El ejemplo más limpio de por qué la propiedad del fichero importa tanto como sus permisos.

Instalación

Una VM Ubuntu Server 24.04 en red aislada, 2 vCPU y 2–4 GB de RAM.

# En una VM desechable, en una red NAT o host-only:
git clone https://github.com/rgomez31UAQ/vulnserver-lab.git vulnserver
cd vulnserver
sudo ./install.sh --install-deps --activate a,b,c

./lab-manager.sh          # estado y control de escenarios
sudo ./audit.sh           # informe de hallazgos, solo lectura
sudo ./harden.sh --apply  # equivalente endurecido, con copias

Juice Shop se publica en el puerto 3000 y UFW lo limita a LAB_ALLOWED_NETS. Por SSH solo entran adminlab y labuser; root nunca.

En la nube, solo por el túnel

Un VPS expuesto es un VPS comprometido en horas. Aquí solo se abre WireGuard.

Un comando

provision.sh crea la VM en Hetzner o Vultr, registra tu clave SSH, levanta un firewall que solo permite UDP 51820 y TCP 22 desde tu IP, sube el proyecto, monta el túnel y descarga los perfiles de cliente.

export HCLOUD_TOKEN=...
./scripts/cloud/provision.sh \
  --provider hetzner --name vulnserver-1

Primer arranque desatendido

Si el repositorio es público, la VM puede instalarse sola con cloud-init: el user-data pesa unos 2,5 KB porque descarga el proyecto en lugar de incrustarlo (Hetzner limita user_data a 32 KiB).

Al terminar: ssh labuser@10.8.0.1 y http://10.8.0.1:3000/. Nada más está publicado.

GitHub Pages es alojamiento estático: esta web presenta el laboratorio, no lo ejecuta. El servidor vulnerable se levanta en tu VM.
